A field write-up · May 2026

I taught Claude Code
to remember things.

For two months I'd been watching the same correctable mistakes recur across sessions — silent commits, narrowed scope, blind 4th deploys. The fix wasn't more agents. It was making the ones I had aware of the institutional memory they live alongside. Here's what I built, why, and what broke.

By Molly Shelestak · senior PM, multi-brand operator, build partner · written for other senior tech builders wondering whether their own Claude Code setup could be doing more.

§ 01

The story — how I got here

I'd accumulated 78 memory files. 12 distilled learned patterns. 13 specialist agents. 21 hooks. A CARL rule system. Three brands of voice routing. None of it was wired together.

A typical session would start fresh. I'd ask Claude to ship a feature. Claude would hit the same Railway deploy trap I'd documented twice before. Or commit content with my Instagram handle wrong. Or quietly swallow a Postgres error and report success. The fix had been written down — in a feedback memory, in a learned pattern, in a project reference doc. Claude just... never read it.

The moment I noticed the recursion was when I caught myself, again, explaining why the Raw Editor in Railway leaks every secret value as plaintext DOM. I'd written that lesson three weeks earlier. It was sitting in my memory directory under secrets-routing. The agent I dispatched to set up the env vars had no idea it existed.

Memory exists. Claude just doesn't read it. The agents work in parallel, in their own context windows, and the archive of everything I'd learned was sitting one filesystem away. — what I told myself the morning I started this build

The four leaks I named

When I sat down to design the fix, I forced myself to make the failure modes concrete. Naming them is half the work — abstract "Claude doesn't remember" gives no traction. Specific leaks do:

  1. Agents skip the patterns mid-flight. I'd written distilled lessons to ~/.claude/skills/learned/. Agents had no instruction to read them.
  2. Project memory never gets read at start. Project-specific gotchas (Railway TTY traps, Supabase MCP scope quirks) lived in project_*.md files. Sessions skipped them.
  3. New learnings don't land at the end. Surprises in a ship session evaporated unless I stopped to write them up — which I rarely did mid-deploy.
  4. The pipeline is a list, not a process. /ship was twelve lines of "dispatch this agent, then that agent." No pre-flight check. No verification that patterns actually got applied. No DoD walk against the spec.

The new /ship closes all four. Pre-flight loads memory. Patterns inject into every agent prompt. A hook gates the deploy stage. A capture step at the end harvests new lessons.

§ 02

Hook vs skill vs agent vs command

Before going further: four words I use a lot. They're easy to confuse and the difference matters. If you've already wired up a Claude Code setup, skim. Otherwise, this is the orientation:

User-typed

Command

Slash commands like /ship or /build. The user types them in chat. Each one is a markdown file whose body becomes the prompt. They're orchestration entry points — they pick which agents run, in what order, against which spec.

/fix · /build · /ship · /write
Auto-loaded by description match

Skill

A method. A markdown file that says "here's how to do X." Claude auto-invokes a skill when the user's request matches its description. Skills load into the current context — they don't run separately.

brainstorming · writing-plans · frontend-design
Explicit · own context

Agent

A role. Has its own context window, its own model (Haiku, Sonnet, or Opus), its own tool palette. The orchestrator dispatches an agent for work that has its own quality bar — UI design, security audit, content QA. Returns a focused output back.

engineer · designer · reviewer · memory-keeper
Lifecycle event

Hook

A shell script wired to a Claude Code event (PreToolUse, PostToolUse, Stop). Runs outside the model — deterministic, fast, can block tool calls. This is where you put rules that must always fire, like "block dangerous commands" or "format on save."

block-dangerous · prettier-format · ship-phase-gate

The mental model: commands route, skills explain how, agents do the work, hooks enforce the rules. The trick is knowing which of the four to reach for. New users put everything in skills; that gets messy fast. Putting deterministic rules in skills is the most common mistake — they belong in hooks.

The whole system has 14 agents, 22 hooks, 40+ skills, and 20 slash commands. Each picked deliberately. Most of the design work is just figuring out which surface this belongs on.

§ 03

Watch one /ship run

Easier to show than describe. Here's what happens when I type /ship deploy nancy phase 12 webhook to railway — a real deploy-shaped ask in one of my live projects.

Step 1 · Pre-flight (a Haiku agent reads memory)

Input
/ship deploy nancy phase 12 webhook to railway

The orchestrator dispatches a small agent called memory-keeper first thing. It detects the project (nancy) from cwd and parses the description for tags.

Output
Inferred tags: [deploy, infra]
Project: nancy

Loading 12 patterns into .ship/2026-05-10-nancy-phase-12/patterns.md:
  · 4 always-load (blocking)
  · 2 project-load (nancy-specific)
  · 6 tag-matched (deploy + infra)

Confirm tags? [y/n/edit]

What happened: memory-keeper globbed every memory file and learned pattern, parsed their YAML frontmatter, and filtered to the dozen most relevant for this ship. Twelve files, not seventy-eight. Now every downstream agent reads patterns.md before doing anything.

Step 2 · The agents work, with patterns injected

Stages 2-8 are the existing /ship flow — product-lead writes a brief, engineer explores, reviewer + security pass — but every Agent dispatch now carries a prompt prefix: 

Apply patterns from .ship/<run>/patterns.md.
Read the file before acting. If a pattern conflicts
with the task, raise NEEDS_CONTEXT — don't silently
override.

Step 3 · The hook gate fires at deploy

Stage 9 is where the real enforcement lives. After every Bash and Agent call inside the ship's directory, a shell hook (ship-phase-gate.sh) checks deploy-log.md for three things:

deploy-log.md after 3 deploys, no pivot section
## Deploy attempt 1
result: fail — uvicorn boot loop

## Deploy attempt 2
result: fail — webhook 502

## Deploy attempt 3
result: fail — same 502
Hook output (blocks next agent dispatch)
{
  "decision": "block",
  "reason": "3-deploy rule triggered:
    3+ deploys without convergence.
    Add a `## Pivot decision` section
    to deploy-log.md before next deploy.
    See learned/deploy-iteration-discipline.md."
}

The lesson behind that block came from a real Railway debugging session in early May. I shipped seven commits in two hours trying to fix an opaque webhook problem; the last three produced no new information because the framework's log panel was frozen. Pushing felt like progress. It wasn't. I wrote up the rule. Now the hook enforces it on me.

Step 4 · Capture (Haiku reads the transcript)

At the end of the run, memory-keeper comes back. It scans the session transcript for correction signals — moments where I said "no," "stop," "actually," or re-prompted after an agent output — and drafts candidate feedback files. It asks me three questions:

  1. "I noticed you corrected me on X. Save this draft as feedback_<slug>.md?" (per draft, y/n/edit)
  2. "What surprised you in this ship that I didn't catch?" (free text or skip)
  3. "Anything from this session that should become a learned pattern, not just a feedback file?" (y/n + which)

Approved drafts move from .ship/<run>/draft-feedback/ into ~/.claude/projects/.../memory/. The MEMORY.md index gets updated. If a theme has crystallised across multiple feedback files, the synthesis hook flags it next session for promotion to a learned/ pattern.

That's one full ship. The previous version of this command did the middle (the agents) without the bookends. The bookends are the point.

§ 05

The memory layer

78 files at last count. Lessons I've learned, project-specific gotchas, references to external systems, my own working profile. Each one with YAML frontmatter that /ship uses to decide what to load.

What a memory file looks like

~/.claude/projects/.../memory/feedback_railway_raw_editor_leaks_secrets.md
---
name: railway-raw-editor-leaks
description: The Raw Editor exposes
  every existing env value as plaintext
  DOM. Use the New Variable UI for adds.
type: feedback
applies-to: [secrets, deploy]
projects: [all]
severity: warning
phase: [deploy, build]
last-validated: 2026-05-10
---

When adding a single env var to a Railway
service, click "+ New Variable" — never
the Raw Editor. The Raw Editor renders
all existing values plaintext into the
DOM, leaking them into your conversation
context if Playwright or screen-share is
active.

**Why:** Caught during a  deploy
when I screen-shared with another agent
and three secrets ended up in chat...
How memory-keeper uses this file

On a /ship with secrets or deploy in the inferred tags, this file gets pulled into patterns.md. Every agent dispatched in that ship reads the rule before acting.

If the agent goes to add an env var, it now knows to use the New Variable UI. The lesson doesn't have to be re-explained.

On the next /ship for a content task (no secrets/deploy tags), this file is skipped — saving context budget for what matters.

The twelve tags

Every file gets tagged with one or more of these. The tags are the join key between feature descriptions and patterns.

deployinfrabuildauthcontentdelegationverificationprocessobservabilitysecretsscopememory

How the selection logic actually works

Three rules, evaluated independently per file:

  1. Always-load if severity: blocking AND projects: [all]. These are the universal rules — the four core patterns about not skipping steps, verifying agent output, using existing skills, and not fabricating numbers.
  2. Project-load if projects contains the active project. nancy ships pull the gotchas; ships skip them.
  3. Tag-load if applies-to intersects the inferred feature tags. A "deploy" feature pulls everything tagged deploy. A "content" feature doesn't.

The union of the three becomes patterns.md. Typical run loads 8-15 files. Selection happens on Haiku, so it's cheap.

Why frontmatter and not embeddings

A semantic search via embeddings would be more flexible. Tags give me debuggability — if a pattern didn't fire when it should have, I can trace the path. Was the file tagged correctly? Were the inferred feature tags right? Did severity trigger always-load? Embeddings hide the audit trail.

§ 07

The 22 hooks — deterministic enforcement

Hooks are bash scripts wired to Claude Code lifecycle events. They don't go through the model — they execute, read JSON from stdin, write JSON to stdout. They're how I make rules that must fire, regardless of whether the agent remembered to.

What a hook actually looks like

~/.claude/hooks/ship-phase-gate.sh (excerpt)
SHIP_DIR=""
DIR="$PWD"
for _ in 1 2 3 4 5; do
  if [ -d "$DIR/.ship" ]; then
    SHIP_DIR="$DIR/.ship"; break
  fi
  PARENT=$(dirname "$DIR")
  [ "$PARENT" = "$DIR" ] && break
  DIR="$PARENT"
done
[ -z "$SHIP_DIR" ] && exit 0

DEPLOY_LOG="$RUN_DIR/deploy-log.md"
DEPLOY_COUNT=$(grep -c "^## Deploy attempt" \
  "$DEPLOY_LOG" 2>/dev/null || true)

if [ "${DEPLOY_COUNT:-0}" -ge 3 ]; then
  if ! grep -q "^## Pivot decision" \
       "$DEPLOY_LOG"; then
    echo '{"decision":"block",...}'
    exit 0
  fi
fi
What this enforces

Walks up from cwd looking for a .ship directory (max 4 levels). If not found, silent exit — every other tool call works normally.

If found, reads deploy-log.md. Counts deploy attempts. If three or more without a Pivot decision section, blocks the next agent dispatch with a JSON refusal.

Result: I literally cannot deploy a fourth time without naming what I'm pivoting away from. The discipline is mechanical, not aspirational.

The full hook catalog runs across PreToolUse (block-dangerous, agent-batch-validator), PostToolUse (prettier-format, content-qa-guarded, ship-phase-gate), Stop (session-retrospective enforces my Definition of Done), SessionStart (carl-loader, synthesize-learnings), and a few specialty events. Twenty-two total.

§ 08

How I built it — a build log

The build itself followed the workflow it eventually encoded. Brainstorm before brief; brief before plan; plan before code; code under two-stage review; capture at the end. The recursion was on purpose.

1 · Brainstorm

Started by surveying what was already there: 78 memory files, 12 distilled patterns. The brainstorming skill (from the Superpowers plugin) keeps you from jumping to implementation too fast. It asked four clarifying questions — what's broken, how heavy a fix, where do new learnings go, how to pick which memories to load. I picked all four pain points. Full overhaul of /ship.

2 · Spec

Wrote a design document at docs/superpowers/specs/2026-05-10-ship-pipeline-v2-design.md. Eleven stages, three new. Kill criterion baked in: after three real /ship runs through Stage 9, simplify back to bolt-on if the patterns aren't paying off. Naming when to give up is itself a discipline.

3 · Plan

22 tasks across 7 phases. Each one with explicit file paths, exact code, exact bash commands, expected outputs. The plan document is what an engineer (or a fresh subagent) would need to implement without further context.

4 · Subagent build

One implementer + one spec reviewer + one code-quality reviewer per task. Eight critical bugs caught across two tiny scripts — all on the code-quality pass after spec compliance was already green. That learning got captured: run both reviewers, even on small files.

The bugs the code-quality reviewer caught

FileBugWhy it mattered
validate-frontmatter.shSilent pass on unclosed frontmatterA file with one --- and no closing fence reported "missing key" instead of "unclosed." Misleading errors during the 18-file retrofit.
validate-frontmatter.shInline-comment manglingtype: feedback # comment tripped tr -d ' ', producing garbage. False negative on valid YAML.
validate-frontmatter.shCRLF + fence whitespace intoleranceFiles saved on Windows or with trailing spaces broke. Realistic for multi-author files.
ship-phase-gate.shgrep -c + || echo 0 stderr leakEmpty deploy-log produced "0\n0" → integer compare crash → noisy stderr on every tool call inside any ship workspace.
ship-phase-gate.shls -1dt mtime orderingMulti-run case picked stale runs over current ones. Hook would gate on the wrong policy.
ship-phase-gate.shDescendant-find vs ancestor-walkHook only fired when cwd was at or above .ship/. Deep cwd missed it. Common case in real work.

Each one would have wasted hours during the retrofit phase or produced wrong behaviour in production. Together they validate the rule that eventually went into memory: always run both reviewers.

§ 09

Meta moment — this site is the proof

The site you're reading was built using /ship v2 itself as the Phase 7 acceptance test. It's the dogfood — the first real production run of the pipeline I'd just shipped.

Stage 1 ran: memory-keeper wrote a real patterns.md for this build, with content/deploy/process tags. Stages 2-8 ran with the patterns prompt prefix injected. Stage 9's hook fired live — I triggered it from inside the run directory and from a 2-level-deep subdirectory, verifying the ancestor-walk fix in production. Stage 11 captured new feedback drafts (one of which is now in memory: ask the audience question before designing — yes, I missed that one).

What broke during the dogfood run:

I built v1 of this site as strict technical reference. Molly's review: "this is too technical… what's a hook versus a skill? where are the examples? references should be actual links." Forced a full rewrite — the version you're reading. The original was an internal docs site for someone who already knew the system. The audience question never got asked. That's now a blocking rule in memory.

§ 10

What I learned — captured to memory

Four feedback memories landed during this build. Each follows the same structure: rule first, then the concrete incident behind it, then how to apply it next time.

Script over heredoc
feedback_script_file_over_multiline_paste.md

When auto-mode blocks self-modification and I have to hand a script back to Molly, write it to a file. The terminal auto-indents pasted heredocs and Python rejects them. Two failed paste attempts before I switched to file-based.

Two reviewers, always
feedback_subagent_review_loops_catch_real_bugs.md

Two small bash files. Eight critical bugs the code-quality reviewer found that the spec reviewer missed. Different bug classes — spec is "does it do what was asked"; quality is "what breaks when input drifts."

Sweep all docs
feedback_sweep_all_docs_when_shipping_config_changes.md

Pushed v1 of the pipeline. Updated the "obvious" docs. Missed architecture.md entirely. Molly caught it. Lesson: grep ALL docs for stale refs before pushing — not the ones I happen to remember.

Ask the audience first blocking
feedback_ask_audience_before_designing.md

Built v1 of this site without asking who it was for. Defaulted to "future Molly" — an internal-docs audience. Molly's actual audience: senior tech builders curious about her setup. Required a full rewrite. Now a hard rule before any external deliverable: multiple-choice audience question first.

One promoted to a learned pattern

The dogfooding pattern crystallised as a learned/ file: when you ship v1 of a new system, the first real run should be using that system to produce its own documentation or release artefact. Forces every gap to surface during the most-attention moment. The recursion is the point.

§ 11

What's still rough — gaps + roadmap

v1 is a vertical slice, not a finished product. The honest list of what hasn't been solved:

Stage 9 is the only enforced gate. Stages 2, 4, 5, 7, 10 have inline reminders only. An agent that skips them won't be hard-stopped. Phase B closes Stages 5 and 10; Phase C closes 2, 4, 7.
Frontmatter coverage is 18 of 78 files. The deploy-tagged subset got the v2 retrofit. The other 60 files don't yet filter into patterns.md at pre-flight, even when they'd match. Phase B finishes the rest.
The full memory-keeper flow is untested in the wild. Validator and hook tests exist. Stage 1 and Stage 11 ran during this site build. But three real runs is the kill-criterion judgment window — we have one.
Self-modification is gated. Editing ~/.claude/settings.json from inside Claude is blocked by the auto-mode classifier. Workaround: a registration script Molly runs from her prompt with the ! bang prefix. Friction, not blocking.
Eleven-stage ceremony is heavy on small features. Hence /build and /fix. Phase C brings memory-awareness to those modes — that design isn't done yet.

Phase B · after three real /ship runs

  • Frontmatter retrofit on the remaining 60 memory files.
  • Per-agent ship-stage + ship-patterns frontmatter on the eight existing agents.
  • Hook gates added on Stage 5 (Decision Lock) and Stage 10 (Handoff).
  • Pattern injection prefix becomes part of every Agent dispatch — currently it's an inline orchestrator habit.

Phase C · after Phase B validates

  • Hook gates on Stage 2 (Brainstorm), Stage 4 (Explore), Stage 7 (Test).
  • /build and /fix get integration via a shared memory-aware skill.
  • patterns.md becomes machine-readable JSON for downstream tooling.
  • MEMORY.md auto-generated from frontmatter.

Kill criterion · when to give up

After three real /ship runs through Stage 9, simplify back to bolt-on (pre-flight + capture only, drop the hook) if any of these are true:

  • < 30% of loaded patterns surface anything actionable across the three runs.
  • Zero new feedback files captured at Stage 11 across the three runs.
  • Hook false-positive rate > 1 in 3 runs.

Naming the kill criterion in advance prevents sunk-cost continuation of an over-engineered pipeline. It's the cheapest insurance you can buy on a build like this.
